# Python 고정 패키지·오프라인 설치 검증

2026-09-13에 새 사본(ItsDangerous 2.2.0, commit 096c8d42545d3b68ea21a4f890fb2b2d8979c0bd)에서 Python 검사기의 엄격 검사와 원본 mutmut 3.7.0 직접 실행을 같은 조건으로 돌려 변이 567개의 집계를 대조했다. 세 상태가 모두 맞아떨어졌고(아래 표), 검사 결과는 품질 기준 미달인 종료 2/qualityFailed다. 통합 명령(`sentinel setup --language python --python-requirements`)으로 같은 프로젝트를 준비하는 경로도 이번에 확인했다.

이 기록은 [실행 계획 Task 2c·2d](https://github.com/hwain-hwang/SENTINEL/blob/main/docs/exec-plans/active/2026-09-sentinel-unified-entry.md)의 준비 단계다. 가상환경은 패키지를 별도로 설치하는 장소이지 파일·네트워크 접근을 막는 보안 경계가 아니다. 아래 최초 호스트 준비에서는 원래 저장소에 접근할 수 있었고 모듈 검색 경로만 분리했다. 이후 컨테이너 설치에서는 SDK·설치 입력만 읽기 전용으로 연결했으며, 두 단계의 근거를 구분한다.

## 현재: 원본 mutmut 직접 실행과의 대조 결과(2026-09-13)

입력은 새 사본 하나다. 검사기 설정은 production `src/**/*.py`, testRoots `tests`, testPatterns `test_*.py`·`__init__.py`, excluded `docs/**/*.py`이고, 원래 시험 요구사항(requirements/tests.txt, freezegun 1.4.0 등)은 통합 명령의 `--python-requirements`가 `<프로젝트>/.sentinel-deps`에 wheel로 설치했다. 문서 설정이나 테스트 파일은 제거하지 않았다.

첫 엄격 검사는 종료 6/backendProcessFailed로 끝났다. 원인은 검사기가 mutmut 실행과 kill 재검증에 쓰는 환경의 PYTHONPATH에 `.sentinel-deps`가 빠져 있어 mutmut의 stats 단계에서 `freezegun`을 못 찾은 것이다(기준선 pytest만 의존성 폴더를 보고 있었다). 검사기를 고친 뒤(회귀 시험 1개, 자체 시험 511개 통과) 다시 실행한 결과가 아래다. 실행 시간 3,421초는 같은 기계에서 Java·TypeScript 시험과 CPU를 나눠 쓴 상태의 값이다.

SENTINEL은 두 번 재실행해 같은 assertion 실패로 재현된 변이만 killed로 세고, 예외로 죽은 변이는 runtimeError로 분리해 kill 비율에서 뺀다. 직접 실행에서 killed로 나온 변이 20개를 표본으로 다시 실행해 보면 AssertionError 4개, pytest.raises의 DID NOT RAISE 1개, TypeError·AttributeError 15개였다. mutmut 3이 인자를 None으로 바꾸는 변이를 많이 만들기 때문에 대부분이 예외로 죽는다.

남은 한계는 두 가지다. 검사 결과와 증거 파일에는 변이별 기록이 없고 집계만 남으므로 변이 단위 대조는 직접 실행의 meta 파일로만 할 수 있다. 통합 명령의 기본 `check`는 승인 전이라 여전히 `--experimental`로만 실제 판정을 받는다.

## SDK 설치 표현 검토의 현재 상태
